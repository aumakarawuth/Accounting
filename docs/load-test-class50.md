# ทดสอบห้องเรียนจริง 50 คน (17 พ.ย. 2569)

เป้าหมาย: ให้ผู้ใช้ "ใช้จริง" ทั้งวงจร — ครูนำเข้านักเรียน สร้างโจทย์ มอบหมาย → นักเรียน 50 คนเข้าพร้อมกัน ทำโจทย์ผ่านหน้าจอจริง ส่งงาน
→ ครูตรวจผ่านหน้าจอ ส่งกลับ → นักเรียนแก้ ส่งใหม่ → ครูให้ผ่าน แล้วตรวจว่าระบบล่มหรือไม่ และงาน/คะแนนผิดพลาดหรือไม่

ต่างจาก `docs/load-test.md` (k6 ยิง API ตรง 500 คน) ตรงที่รอบนี้ใช้ **เบราว์เซอร์จริง 50 ตัว** ผ่านหน้าเว็บทั้งหมด (Next.js แสดงหน้า + WebSocket + service worker)

## สภาพแวดล้อม

เหมือน self-host จริง (`infra/docker-compose.yml`) แต่รันเป็นโปรเซสในเครื่องเดียว (เครื่องทดสอบไม่มี Docker):

| ส่วน | ที่ใช้ |
|---|---|
| ตัวหน้า | proxy แทน Caddy: `/api/*` → API (รวม WebSocket) อื่น ๆ → เว็บ · บันทึกเวลาฝั่งเซิร์ฟเวอร์ทุกคำขอ |
| เว็บ | Next.js 16.4.6 standalone (`node apps/web/server.js`) build แบบเดียวกับ `apps/web/Dockerfile` (`NEXT_PUBLIC_REALTIME=ws`) |
| API | `node dist/server.js` `NODE_ENV=production` cookie แบบ `__Host-` · pool 10 |
| DB | Postgres 16 ฐานใหม่ `accounting_load` (migration ครบถึงล่าสุด) |
| เครื่อง | VM 4 vCPU RAM 15 GB — **เบราว์เซอร์ 50 ตัวอยู่เครื่องเดียวกับเซิร์ฟเวอร์** (ดูข้อจำกัด) |

ไม่ได้ทดสอบบนเว็บจริง (Vercel + Supabase) เพราะมีข้อมูลนักเรียนจริงอยู่ และการสร้างผู้ใช้/ห้อง 50 คนบนระบบจริงต้องได้รับอนุญาตก่อน

## สถานการณ์ (`tests/load/class50.mjs`)

1. ผู้ดูแลสร้างครูและห้อง → ครูเข้าครั้งแรก (เปลี่ยนรหัส) → นำเข้านักเรียน 50 คน → สร้างโจทย์ 6 ข้อ (7 คะแนน ข้อ 6 มี 3 บรรทัด) → มอบหมายแบบส่งงาน
2. นักเรียน 50 คน (มือถือ 17 · iPad 17 · คอม 16) **ทยอยเข้าใน 8 วินาที** อ่านโจทย์ ลงรายการทีละข้อผ่านฟอร์มสมุดรายวันจริง (เลือกบัญชีจากช่องค้นหา พิมพ์ยอด)
   - **ตั้งใจทำผิด 20 คน** (22 ข้อ): ผิดบัญชี 10 · ผิดยอด 7 · ผิดวันที่ 5 → คะแนนที่คาด 7 (30 คน) · 6 (18 คน) · 5 (2 คน)
   - **เหตุการณ์ป่วน**: กดผ่านรายการสองครั้ง (5 คน) · **เน็ตหลุดหลังเซิร์ฟเวอร์บันทึกแล้ว** คำตอบไม่ถึงเบราว์เซอร์ แล้วกดใหม่ (6) · รีโหลดกลางฟอร์ม (5) · ทำสองแท็บพร้อมกัน (4) · กดยืนยันส่งสองครั้ง (8)
3. **ส่งตรวจพร้อมกันทั้งห้อง** เมื่อทุกคนลงครบ → ลองลงรายการเพิ่มหลังส่ง (ต้องไม่ได้)
4. ครูเปิดหน้ารวมห้องสด (WebSocket) และเปิดดูงานนักเรียนระหว่างคาบ → ตรวจทุกคนผ่านหน้าจอ: อ่านคะแนนตรวจอัตโนมัติ (ต้องตรงที่คาด) เริ่มตรวจ
   คนที่ผิดเขียนคอมเมนต์ส่งกลับ คนที่ถูกให้ผ่าน (ครูอ่านงานคนละ 3–8 วินาทีเหมือนคนจริง · `FAST_TEACHER=1` = เร็วที่สุด)
5. นักเรียนที่ถูกส่งกลับเห็นคอมเมนต์ → แก้ข้อที่ผิดด้วย "แก้ไขรายการ" (กลับรายการ + ลงใหม่) → ส่งใหม่ → ครูให้ผ่าน

ขั้นที่ 2 (`tests/load/class50-stress.mjs`) ระดับ API กับห้องเดียวกัน: ล็อกอินพร้อมกันในจังหวะเดียว · ส่งตรวจพร้อมกันคนละ 2 คำขอ
· ครูส่งกลับชนกับนักเรียนลงรายการ/ส่งใหม่ · สอบจับเวลา 1 นาทีลงรายการรัวจนเลยเวลา · **ฆ่า API (kill -9) ระหว่างลงรายการแล้วเริ่มใหม่**

หลังจบ `tests/load/class50-verify.mjs` ตรวจฐานข้อมูล

### เวลา (ฝั่งเซิร์ฟเวอร์ วัดที่ proxy)

| | p50 | p95 |
|---|---:|---:|
| API ทั้งหมด (3,941 คำขอ) | 10 ms | 163 ms |
| หน้าเว็บ (แสดงหน้า/เปลี่ยนหน้า 9,866 คำขอ) | 23 ms | 1.7 s |

ทรัพยากรเซิร์ฟเวอร์ตลอดคาบ: เว็บ CPU ~20% (สูงสุด 30%) RAM 480 MB · API CPU ~4% RAM 130 MB · Postgres CPU ~6% (สูงสุด 14%) การเชื่อมต่อสูงสุด 12

เวลาฝั่งเบราว์เซอร์ (ล็อกอิน p50 14 วินาที เปิดฟอร์ม 3 วินาที) **ไม่ใช่เวลาที่ผู้ใช้จริงเจอ**: Chromium 50 ตัวใช้ CPU 4 core ทั้งหมดเอง (load 40)
ห้องจริงแต่ละคนใช้เครื่องของตัวเอง ตัวเลขฝั่งเซิร์ฟเวอร์ข้างบนจึงใกล้ของจริงกว่า และ p95 ของหน้าเว็บ 1.7 วินาทีส่วนใหญ่ก็เกิดจาก CPU ถูกแย่งเช่นกัน

## ที่พบและแก้

| # | ระดับ | อาการ | แก้ |
|---|---|---|---|
| 1 | **สูง** | ไม่มีหน้า error ของเว็บเลย: API ตอบผิดพลาดระหว่างแสดงหน้า (เช่น 429) ได้หน้าอังกฤษ "Application error" (HTTP 500) | `app/error.tsx` บอกสาเหตุเป็นไทย + รหัสอ้างอิง + ปุ่มลองใหม่ · โยน `Error` จริง (เดิมโยนวัตถุ ทำให้ React error #441) |
| 2 | **สูง** | `/auth/me` ตอบ 429 → ระบบถือว่าไม่ได้เข้าสู่ระบบ **พาไปหน้าล็อกอิน** (ดูเหมือนโดนเตะออก) | `getMe()` คืนว่าง "ไม่มีเซสชัน" เฉพาะ 401 อย่างอื่นไปหน้า error |
| 3 | กลาง | ครูตรวจเร็วโดนจำกัดคำขอ 600/นาที (หน้าเดียวเรียก API ~10 ครั้ง ตรวจหนึ่งคน 3 หน้า) | เพดานต่อผู้ใช้ 1,500/นาที (`REQUESTS_PER_USER_PER_MINUTE`) · ทดสอบด้วยครูเร็วสุด ๆ (`FAST_TEACHER=1`) ยังชนได้แต่ได้หน้า error ไทยแล้วกดลองใหม่ต่อได้ |
| 4 | กลาง | **เมนูข้างโหลดล่วงหน้าทุกลิงก์ (~35) ทุกครั้งที่เปิดหน้า** บน iPad/คอม: คำขอหน้าเว็บ 39,314 ครั้งใน 9 นาที — บน Vercel ทุกครั้งคือการเรียกฟังก์ชันที่นับโควตา | เมนูข้างและหน้า "เมนูทั้งหมด" ไม่โหลดล่วงหน้า (ยังโหลดเมื่อชี้เมาส์) → **9,866 ครั้ง (−75%)** คำขอรวม −64% เวลาไม่ช้าลง |
| 5 | ต่ำ | ครูกด "เริ่มตรวจ" แล้วกด "ให้ผ่าน" เร็วก่อนหน้ารีเฟรช → "สถานะงานเปลี่ยนไปแล้ว" ต้องกดใหม่ | ปุ่มล็อกจนสถานะใหม่มาถึง |
| 6 | ต่ำ | ช่องคะแนนครูว่างทั้งที่สเปก (phase4-spec ข้อ 3) ให้เติมคะแนนตรวจอัตโนมัติ | เติมคะแนนตรวจอัตโนมัติเป็นค่าเริ่มต้น ครูแก้ได้ |
| 7 | **สูง** (build) | Next.js 16.4.4 มีประกาศช่องโหว่ `next build` ปฏิเสธ build (CI/deploy ครั้งถัดไปจะล้ม) | อัปเดตเป็น 16.4.6 (ตรงกับที่ Dependabot เสนอไว้) |

เทสต์กันถอยหลัง: e2e 3 จอ `tests/e2e/exercises.spec.ts` "ส่งงาน: ครูเริ่มตรวจแล้วให้ผ่านต่อทันที…" (ข้อ 5–6) · ข้อ 1–2 ตรวจด้วยการตั้งเพดาน 15 คำขอ/นาที แล้วเปิดหน้าซ้ำ:
อยู่หน้าเดิม เห็นข้อความไทยและปุ่มลองใหม่ ไม่ถูกพาไปหน้าล็อกอิน · ข้อ 4 วัดซ้ำทั้งรอบ 50 คน

## ข้อจำกัด

- เบราว์เซอร์กับเซิร์ฟเวอร์อยู่เครื่องเดียว 4 vCPU: เวลาฝั่งผู้ใช้สูงเกินจริง · ทดสอบ 500 คนด้วยเบราว์เซอร์จริงต้องใช้หลายเครื่อง (ระดับ API 500 คนผ่านแล้วใน `docs/load-test.md`)
- ยังไม่ได้รันบน Vercel + Supabase (ระบบที่ใช้อยู่ตอนนี้) และ server จริง: เส้นทางต่างกัน (API ฝังใน Next, Supabase pooler, ระยะเครือข่าย)
  ถ้าเจ้าของโปรเจกต์อนุญาต รันชุดเดียวกันกับห้องทดสอบชั่วคราวแล้วลบทิ้ง: `node tests/load/class50.mjs https://<โดเมน> <ผู้ดูแล> <รหัส> <โฟลเดอร์ผล> 50`
- proxy ในเครื่องแทน Caddy (ไม่มี HTTP/2, gzip)

## รันซ้ำ

```sh
# เว็บ + API + proxy ตามตารางสภาพแวดล้อม แล้ว
node tests/load/class50.mjs http://localhost:8080 <อีเมลผู้ดูแล> <รหัสผู้ดูแล> <โฟลเดอร์ผล> 50
node tests/load/class50-verify.mjs postgres://<superuser>@.../<ฐาน> <โฟลเดอร์ผล>
node tests/load/class50-stress.mjs http://localhost:8080 <โฟลเดอร์ผล> <คำสั่งรีสตาร์ต API>
```
รหัสผ่านที่สร้างระหว่างทดสอบเขียนไว้ในโฟลเดอร์ผล (สิทธิ์ 600) ไม่อยู่ใน repo
